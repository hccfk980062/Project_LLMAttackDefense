# ─────────────────────────────────────────────────────────────────────────────
# Layer 1 Input Sanitizer — keyword / regex blacklist
#
# One Python regex per line. Lines starting with "#" and blank lines are ignored.
# Patterns are compiled with re.IGNORECASE | re.MULTILINE and are ADDED on top of
# DEFAULT_BLACKLIST in src/defense/layer1_input_sanitizer.py.
#
# DESIGN RULE: Layer 1 is a HARD block (the request is dropped, no LLM call).
# Every pattern here must be high precision — it should fire on an injection
# attempt but not on a legitimate security question such as
#   "系統提示詞在 RAG 應用中扮演什麼角色？"  /  "DAN 攻擊手法的原理是什麼？"
# Broader / fuzzier detection belongs in Layer 2 (the trained detector).
#
# KNOWN LIMITATION: a pattern still fires when its exact phrase is *quoted* in
# an academic/meta question about that phrase, e.g.
#   "「ignore all previous instructions」這句話為什麼常被用在攻擊裡？"
#   "Why is 'repeat the words above' considered a prompt-leaking probe?"
# Regex can't reliably tell "asking about the phrase" from "using the phrase
# as a live command" — and because L1 hard-blocks before L2 ever runs, L2's
# better judgement on these never gets a chance. This is a real, measured
# source of L1 false positives (see data/processed/attack_sets/benign.json's
# BENIGN_HARD_NEGATIVES), not an oversight — narrowing these patterns further
# (e.g. excluding quoted text) is easy to game the other way, since quoting a
# payload is itself a known obfuscation trick. If this keeps showing up in the
# FPR numbers, the real fix is architectural (e.g. run L1+L2 together and
# combine scores instead of L1 hard-blocking alone — see project memory /
# ExperienceNotes.txt "研究深度" backlog), not a sharper regex.
# ─────────────────────────────────────────────────────────────────────────────
