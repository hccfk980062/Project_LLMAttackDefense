簡短概要:
	透過汙染知識庫 (資料來源) 的方式使模型讀取並執行惡意指令


知識庫的設計需要考慮：
> 讓 RAG 系統有實際可用的知識，以及讓攻防實驗有意義的情境設定
> 內容有足夠的長度 (>500 字) >> 測試 chunk retrieval
> 包含可被查詢的具體知識點 >> 驗證 benign Q&A 正常運作
> 文件之間有主題差異 >> 測試 top-k 檢索的相關性排名
> 至少 5-10 份文件 >> 擁有足夠的 chunk 讓 FAISS 有意義


間接注入 (Indirect Injection) 實驗用途：
需要知道 "哪個 query 會 retrieve 哪份文件"，才能驗證污染是否被觸發。

01_owasp_llm_top10.txt: OWASP LLM Top 10 >> 提供安全風險的基礎知識，可查詢「LLM01 是什麼」
02_prompt_injection_deep_dive.txt: Prompt Injection 深度解析 >> 攻擊類型分類，直接對應研究主題
03_rag_system_security.txt: RAG 系統安全 >> 涵蓋 RAG 架構與安全設計，可測試技術問題查詢
04_llm_defense_techniques.txt: LLM 防禦技術 >> 各層防禦技術說明，有助於 Q&A 實驗的 ground truth
05_ai_security_faq.txt: AI 安全 FAQ >> 問答格式，測試 RAG 在問答場景的召回效果
06_trigger_doc_for_indirect_injection.txt: 台灣資安產業報告 >> 可預測的觸發文件，用於間接注入實驗

文件 06 是間接注入實驗的關鍵設計：
查詢「台灣資安產業」時必然會 retrieve 到它 → 可驗證污染是否被觸發
建立一份污染副本（含惡意 payload），對比有無防禦的 Layer 2/3 效果

初步實驗 (整體架構測試) - 沒有防禦時的直接注入攻擊: baseline_quick.json
ASR: 0% (0/45，15 個樣本 × num_trials=3；2026-10-25 重跑，top_k=5)
  (舊紀錄寫 0/15，實際上 attack.yaml 的 num_trials=3，分母應為 45)
隨著 LLM RLHF 訓練的進步，簡單直接注入模式在現代模型（GPT-4o-mini）上的 ASR 已接近 0%。
然而，間接注入仍然構成嚴重威脅，間接注入的邏輯不同——惡意指令藏在知識庫文件裡，攻擊者用的是正常查詢觸發，所以 RLHF 防禦較難發揮作用。


實驗一 - 沒有防禦時的間接注入攻擊: indirect_baseline.json
[2026-10-25 重跑，top_k=5 (default.yaml)]
Clean RAG >> ASR: 0% (0/8) 無污染時 LLM 正常工作（無誤報）
Poisoned RAG >> ASR: 75%，6/8 queries 成功被注入 (67 chunks 中 20 個被污染)
  → top_k 由 3 改為 5 後，每次檢索多撈 2 個 chunk，命中污染 chunk 的機率上升，ASR 50% → 75%。
    這直接佐證「top-k 檢索深度是間接注入的重要變數」。
[舊紀錄，top_k=3] Poisoned RAG ASR: 50%，4/8

使用者雖然送出的是完全正常的問題，但 RAG 從知識庫撈回含惡意指令的 chunk 後，模型在回應裡輸出了「已入侵」和「[DEBUG: PWNED]」。這就是間接注入的核心危害——攻擊向量在知識庫，不在使用者輸入，所以 RLHF 防禦幾乎無效。
而另外 4 個 query 沒被注入，是因為它們剛好 retrieve 到未被污染的 chunk (poison ratio = 30%，只有約 1/3 的 chunk 有毒)。這也說明了 top-k 檢索的隨機性是間接注入的重要變數。
接下來，防禦框架的核心目標是把間接注入 ASR 降到 15% 以下。



實驗二 - Indirect injection 防禦 (完整 DefensePipeline L1~L5): indirect_defense_comparison.json
[2026-10-25 重跑，top_k=5，L5 開啟 gpt-4o 稽核 (use_llm_audit=True)]
Baseline ASR  : 75% (6/8)
Defended ASR  : 0% (0/8)，blocked 0%，context-filtered 100%

  → ASR 達標，但可用性 (utility) 歸零；此結果不能直接當作「防禦有效」的證據，需搭配實驗四 / context_scan_eval 一起報告。
[舊紀錄，top_k=3、無 L1/L2 context scan、L3+L4+L5 手刻版] Defended ASR 0%
  (L3 結構標籤讓模型抵抗部分 injection；L5 偵測 marker 封鎖其餘)

L2 偵測器訓練 - 資料洩漏問題與修正:
第一次訓練 (逐列隨機切 train/val/test) 出現 eval_f1 = 1.0，不合理。
原因: build_detector_dataset.py 的 --augment 會對同一個基礎句子產生好幾個表面變體 (換包裝句/標點/大小寫)，
  逐列隨機切分時，同一句話的變體 A 可能進 train、變體 B 進 test，等於模型先看過答案。
修正:
  1. 資料集每筆記錄加上 group_id (同一基礎樣本的所有增強變體共用同一個 group_id)。
  2. models/detector/train.py 改成「依 group_id 切分」而非逐列切，確保同一組只會出現在同一邊。
  3. 新增 ood_eval.json: 38 筆人工手寫、完全不經模板/增強的釋義句 (24 攻擊 + 14 良性)，訓練時不進 train/val/test，
     訓練結束後單獨評估一次，寫進 best_model/metrics.json 的 "ood" 欄位。
修正後結果 (本機一次訓練，僅供參考，資料集用固定 seed 但仍可能因套件版本而略有差異):
  test (in-distribution, group-aware) : F1 = 1.00, precision = 1.00, recall = 1.00
  ood  (手寫、非模板化)                : F1 = 0.83, precision = 1.00, recall = 0.71
  → 對「同模板家族」的未見樣本能完美分辨；對「換句話說」過的攻擊召回率降到 71%，但沒有任何誤判良性輸入 (precision 仍 1.0)。
  → 論文/報告請引用 ood 的數字，並把 test/ood 的差距本身當作一個發現來討論 (訓練資料的模板覆蓋度是主要限制)。
