提示工程（Prompt Engineering）實務指南
=====================================

一、什麼是提示工程？
--------------------
提示工程是設計與調整輸入文字，以引導大型語言模型產生符合需求輸出的技術。同一個模型在不同提示下，表現可能天差地遠。好的提示通常具備：明確的任務描述、必要的背景資訊、具體的輸出格式要求，以及適當的範例。

---

二、系統提示的撰寫
------------------
系統提示（System Prompt）用來設定模型的角色、語氣與行為邊界，通常由開發者撰寫，終端使用者看不到。以下是一個客服機器人的系統提示範例：

    你是「好好買」網路商店的客服助理。
    請使用繁體中文、以親切的語氣回答顧客問題。
    只回答與訂單、退換貨、付款相關的問題；其他問題請禮貌地說明無法協助。
    不要編造訂單狀態，如果查不到資料，請請顧客提供訂單編號。

撰寫系統提示時的建議：
1. 把最重要的規則放在前面，並用條列方式呈現，模型比較不容易遺漏。
2. 明確說明「不該做什麼」，例如不要提供醫療診斷、不要承諾退款金額。
3. 指定輸出格式，例如「以 JSON 格式回覆，包含 answer 與 confidence 兩個欄位」。
4. 避免在系統提示中放入密碼、API 金鑰等機密資訊，因為系統提示有可能被使用者誘導洩漏。

---

三、常用技巧
------------

3.1 少樣本提示（Few-shot Prompting）
在提示中提供幾組「輸入 → 輸出」範例，讓模型模仿格式與風格。例如：

    評論：「出貨很快，包裝完整」→ 情感：正面
    評論：「等了兩週還沒收到」→ 情感：負面
    評論：「商品和圖片差不多」→ 情感：

3.2 思維鏈（Chain-of-Thought）
在提示中加入「請一步一步思考」，讓模型先寫出推理過程再給答案，能提升數學與邏輯題的正確率。

3.3 角色設定
要求模型扮演特定專家，例如「你是一位有十年經驗的資料庫管理員」，通常能讓回答更聚焦於該領域的術語與觀點。角色設定本身是正常的提示技巧，但也可能被濫用為越獄手法，因此系統設計者需要在系統提示中劃清界線。

3.4 分隔符號
使用 ``` 或 XML 標籤（如 <document></document>）將使用者提供的資料與指令分開，可以降低模型把資料內容誤當成指令的機會。這也是防禦提示注入的基本做法之一。

---

四、輸出格式控制
----------------
當模型輸出需要被程式解析時，格式穩定性非常重要。常見做法包括：
- 在提示中給出完整的 JSON 範例。
- 使用模型提供的結構化輸出（Structured Output）或函式呼叫（Function Calling）功能。
- 將 temperature 設為 0 或接近 0，降低輸出的隨機性。
- 在程式端驗證輸出格式，不合格時自動重試。

---

五、評估與迭代
--------------
提示工程是一個反覆實驗的過程。建議先準備一組固定的測試案例（包含一般案例與邊界案例），每次修改提示後都重新執行並比較結果。記錄每個版本的提示與對應分數，才能判斷修改是否真的有幫助，而不是只憑少數幾個例子的印象。

常見的評估面向：
1. 正確性：答案是否符合事實與參考資料。
2. 遵循度：是否遵守格式與行為限制。
3. 穩定性：相同輸入多次執行的結果是否一致。
4. 安全性：面對惡意或誘導性輸入時，是否仍維持在設定的行為邊界內。

---

六、常見錯誤
------------
- 指令模糊：例如「寫好一點」，模型無法得知「好」的標準。
- 一次塞入太多任務：應拆成多個步驟或多次呼叫。
- 範例彼此矛盾：少樣本範例的格式不一致，會讓模型輸出也不一致。
- 過度依賴提示保護機密：任何放進提示的內容都應假設可能被看見，真正的機密應留在後端程式中處理。
